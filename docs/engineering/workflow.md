# 规格驱动开发工作流

## 一次任务

1. 检查 git status，识别用户已有改动；读核心规则、架构和功能 SPEC/SDD。
2. 指定需求/任务/验收 ID、目标、非目标、依赖、修改路径和风险；未确定的公共行为先补规格。
3. 先契约和失败行为，再用例/纯引擎，再适配器，最后 UI；公共变更、安全边界和竞争语义要有有意义的回归。
4. 本地执行适用检查；失败定位根因，不靠放宽断言或重跑掩盖。
5. 按 [三视角](review.md) 自审；可以同一人执行，但不能称为独立评审。
6. 同步登记表状态与实际实现位置，新增证据报告；文档索引和契约同时更新。
7. 汇报变更、实际验证、未执行原因、风险和回退。公开部署或不可逆操作遵守用户授权与环境规则，不因模板额外重复询问。

## 设计、实现和证据分开

| 状态 | 准入证据 |
|---|---|
| design=baseline | 需求/SDD/ADR 可追踪，契约和验收定义完整；不表示应用完成 |
| implementation=planned | 尚无业务实现 |
| in_progress | 已开始任务，登记修改范围/阻碍 |
| implemented | 需求已有源码位置，仍可能缺运行验收 |
| verified | 适用检查实际通过，正反/竞争与人工项有报告，未执行关键项不得升级 |
| released | 真实环境部署和发布门禁通过，版本与回退可查 |

功能状态唯一写 docs/feature-registry.json。检查报告是冻结记录；后续测试变化新建报告，不覆盖过去失败。风险接受不能替代硬性发布门槛。

## 测试选择

低风险文案/可逆内部小改不制造镜像测试；运行文档检查即可。公共运行规则改动至少覆盖独立手工正反例；数据/权限/并发增加真实数据库与负测；UI 变化做正常操作浏览器回归；发布补真实环境/手机/恢复。

CI 当前只跑已存在的文档和契约检查。源码落地的同一次提交必须接入受影响模块的 lint/typecheck/test/build/边界检查；从“未实现”升级前要把适用门禁从计划变成实际任务。命令不能使用空脚本、跳过全部测试或忽略失败。

## 紧急修复

可以先恢复已授权服务，但保留触发、影响、修复、回退与验证；建立后补规格任务并明确责任，不能永久省略。发现相邻无关问题另记任务，不夹带大重构。
